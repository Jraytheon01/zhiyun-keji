## 3. 产品闭环与系统职责

主产品闭环：

**课程录音或文本导入 → 课程知识本 → TeleAgent 复盘/导图/检测/跨课回顾 → 完整对话回流 → 平台 AI 独立提炼 → 长期记忆与知识状态 → 个性化下一步 → 下一次课程继续验证**

职责边界：

- TeleAgent：自然交互、工具编排、学习过程和产物生成。
- 智云课迹 Skill：规定四种场景的流程、取证方式、结束语和回流动作。
- 教育 MCP：按 `phone` 隔离读取课程、检索课程原文、读取学习上下文，并提交完整对话。
- 平台 AI：课程结构化、对话复核、记忆候选提炼、知识状态更新、档案问答和计划生成。
- 平台数据库：保存课程权威数据、对话证据、派生状态和可撤销的长期档案。
- Milvus：只做语义召回，不充当权威事实库。

“为什么有 TeleAgent 又有平台 AI”是答辩内参，不是主 PPT 的主动展示页。主 PPT 只需自然展示：TeleAgent 负责把学习聊起来，平台把一次互动沉淀为下一次可用的成长依据。

## 5. 三种数据存储各自保存什么

### 5.1 MySQL：课程与课程索引的权威数据

- Docker 容器：`meeting-assistant-mysql-1`
- 本机端口：`3307`
- 独立数据库：`zhiyun_learning`
- 课程主表：`user_meeting_info`
- 课程逐字稿分段：`user_meeting_content`
- 异步索引状态：`recordings`、`ingest_jobs`
- 课程切块与结构事实：`chunks`、`facts`、`todos`
- MCP 鉴权：`mcp_api_keys`，只保存 Key 的 SHA-256 哈希与 `phone` 映射，不保存明文 Key。

字段名沿用既有录音底座以复用成熟 ingest 代码，但已经放进独立教育数据库，不会读取会议业务库。

### 5.2 SQLite：平台侧可信长期状态账本

- 文件：`zhiyun-keji-interactive-prototype/data/zhiyun_keji.sqlite3`
- 权威范围：TeleAgent 任务、回流原始对话、平台洞察、长期记忆元数据、知识状态、计划、档案问答历史。

主要表：

- `teleagent_run`：一次学习互动的 `run_id`、课程、场景、状态与结果。
- `learning_dialogue_turn`：回流的关键原始对话 turn。
- `dialogue_insight`：误区、理解、提问、策略、自我纠正和待验证项。
- `learning_memory`：可复用的长期记忆候选/有效记忆，含 `vector_id` 和来源。
- `learning_memory_evidence`：记忆与 `run_id`、课程、turn、原文引用的关联。
- `mastery_state`：知识状态及证据次数、最近理由；不因“课程讲过”直接变为已掌握。
- `growth_plan`：下一步学习计划和完成反思。
- `learning_event`：课程、互动、平台分析和计划形成的成长轨迹。
- `archive_chat_message`：问课迹 AI 的本地聊天记录。
- `course_import_job`：页面导入的异步任务状态。

### 5.3 Milvus：两个语义索引边界

- Docker 容器：`meeting-assistant-milvus-1`
- 本机端口：`19530`
- 独立数据库：`zhiyun_learning`
- 课程集合：`zyk_learning_chunks`、`zyk_learning_facts`
- 平台长期记忆集合：`zyk_learning_learning_memory`
- Embedding：默认 `doubao-embedding-text-240715`，默认维度 `2560`
- 距离度量：COSINE

Milvus 只保存向量、ID 和少量检索过滤字段。命中后必须回到 MySQL/SQLite 读取完整记录、来源和状态；“语义相似”不等于“事实正确”，也不等于“学生已掌握”。

## 6. 长期记忆如何实现

### 6.1 受控回流

1. 平台创建 `teleagent_run`，生成唯一 `run_id`，并固定 `course_id + phone + action`。
2. 用户在 TeleAgent 完成学习后发送结束语。
3. Skill 调用 MCP `complete_learning_interaction`，提交摘要、关键完整对话、初步标注和产物。
4. MCP 先验证课程属于当前 Key 映射的 `phone`，再回调平台：
   `POST /api/internal/learning-interactions`。
5. 平台再次校验 `run_id + phone + course_id + action`，确保归属、场景和幂等一致。

### 6.2 平台 AI 提炼

平台 AI 不简单接受 TeleAgent 的结论，而是同时读取：

- 课程标题、摘要和逐字稿；
- 学生原话、TeleAgent 提示和自我纠正过程；
- 与本次问题语义相关的历史记忆；
- TeleAgent 的摘要只作为参考标注。

输出结构化 JSON：本次摘要、涉及知识点、真实提问、对话洞察、记忆候选、知识状态更新和下一步行动。

重要约束：

- 单次回答不能直接固化为人格、能力或稳定偏好。
- “课程中出现过”不等于“已经掌握”。
- 提示后答对与独立答对是不同证据等级。
- 候选记忆保留来源，可继续验证、纠正、失效或撤销。
- 同一 `run_id` 重复回流时幂等返回，不重复污染记忆。

### 6.3 向量化与召回

1. `learning_memory` 先在 SQLite 写入权威记录，并生成稳定 `vector_id`。
2. `platform_memory.py` 将“标题 + 内容 + 知识点”发送 Embedding 接口。
3. 向量写入 `zyk_learning_learning_memory`，同时保存 `learner_id`、`course_id`、类型和知识点。
4. 搜索时必须用 `learner_id` 过滤，取回 top-K `vector_id + similarity`。
5. 再按 `vector_id` 回查 SQLite，得到完整内容、置信度、状态与证据链。
6. 平台 AI 将召回记忆与 `mastery_state`、近期事件一同注入上下文，生成回答或计划。

这套机制的核心不是“让向量库记住一切”，而是：**向量负责找到可能相关的过去，状态账本和证据负责决定当前能相信什么。**

## 7. 平台内置 AI 做什么

实现入口：`platform_services.py` 中的 `AIService`。

主要方法：

- `generate_demo_course`：根据课程主题、时长范围和说话人数生成模拟转写 JSON。
- `review`：将课程逐字稿整理为摘要、课程主线、学习目标、知识点、原文依据和知识关系。
- `course_relations`：比较本课与历史课程的前置、补充、迁移和易混淆关系。
- `analyze_learning_dialogue`：结合课程原文、完整对话和历史记忆，提炼长期学习依据。
- `growth_summary`：结合知识状态、记忆、课程和互动生成阶段总结与推荐计划。
- `answer_learning_archive`：只依据当前学习者档案回答“我哪里薄弱、期末先复习什么”等问题，并附证据引用与边界。

模型通过 OpenAI-compatible API 调用火山 Ark；密钥只在：

`zhiyun-keji-interactive-prototype/.env`

禁止把 `.env`、Ark Key、MySQL 密码、MCP 明文 Key写入 Git、PPT、截图或聊天正文。

## 10. PPT 与视频接手规则

主 PPT 收束为三个用户可感知的核心亮点：

1. **让课程被看懂**：课程知识本、知识脉络、原文依据和跨课关联属于同一个亮点。
2. **让课程继续学**：TeleAgent 四种学习场景和真实多轮交互属于同一个亮点，不再分开重复命名。
3. **让成长有迹可循，并产生个性化下一步**：对话回流、长期记忆、成长中心和课迹 AI 推荐属于同一条价值链。

亮点不等于页数。每个亮点可以根据模板和素材占一至两页：一页讲功能全貌，另一页讲真实案例；空间不足时合并呈现。最后可用一条真实动线证明本次互动会改变下一次学习。

不要把“为什么要两个 AI”做成主汇报的两页。该内容只放答辩备份页，在评委追问时解释。

建议视频完整展示：

**导入一节课 → 查看课程知识本 → 选择学习检测 → 复制极简任务并打开 TeleAgent → 学生暴露理解偏差并在提示后纠正 → 结束并回流 → 成长中心出现洞察与待验证记忆 → 问课迹 AI 获取下一步计划。**
